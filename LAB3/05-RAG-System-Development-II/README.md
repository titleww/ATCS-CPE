## 1. บทนำและสถาปัตยกรรมของระบบที่พัฒนาขึ้นจริง (System Architecture)

ระบบ RAG ที่พัฒนาขึ้นในโครงงานนี้ ออกแบบมาเพื่อเป็นระบบสืบค้นและตอบคำถามเชิงลึกทางดาราศาสตร์ ฟิสิกส์ดาราศาสตร์ และเทคโนโลยีอวกาศ โดยใช้สถาปัตยกรรม **Two-Stage Hybrid Retrieval-Augmented Generation** ประกอบด้วยส่วนประกอบหลักดังนี้:

* **Knowledge Base:** `data/astronomy_knowledge_base.txt` รวบรวม 104 คู่คำถาม-คำตอบ (191 Chunks) ครอบคลุม 4 หมวดหมู่ (ระบบสุริยะ, วัตถุในห้วงอวกาศลึก, การสำรวจอวกาศ, ฟิสิกส์ดาราศาสตร์)
* **Chunking Strategy:** `CHUNK_SIZE = 400` ตัวอักษร, `CHUNK_OVERLAP = 50` ตัวอักษร
* **Embedding Model:** `paraphrase-multilingual-MiniLM-L12-v2` (384 มิติ พร้อม $L_2$ Normalization)
* **Dual Indexing:** FAISS (`IndexFlatIP`) สำหรับ Dense Semantic Search ควบคู่กับ `BM25Okapi` (ตัดคำภาษาไทยด้วย `pythainlp`) สำหรับ Exact Keyword Search
* **Hybrid Fusion:** Reciprocal Rank Fusion (RRF) ด้วยค่าคงที่ $k = 60$
* **Re-ranking Engine:** โมเดล Cross-Encoder `BAAI/bge-reranker-v2-m3` ทำงานแบบ Two-Stage (`CANDIDATE_K = 20` $\rightarrow$ `TOP_K = 3`)
* **Generation & Fallback:** Ollama (LLaMA 3.1 8B, Temperature = 0.2) พร้อมระบบสำรอง `NoLLM` Extraction Engine

### ⚡ ขั้นตอนที่ 3: Retrieval & Scoring Fusion (การค้นคืนและการรวมคะแนน)

#### 🔴 ปัญหาที่ 3.1: Dense Search ค้นหาชื่อเฉพาะและตัวย่อดาราศาสตร์ไม่พบ (สอดคล้องกับโจทย์ที่ 6 และโจทย์ที่ 8)
* **สาเหตุของปัญหา:** ชื่อรหัสและคำศัพท์เฉพาะทาง เช่น *"JWST"*, *"TON 618"*, *"M87*"*, *"LIGO"* โมเดลเวกเตอร์มักมองเป็นคำแปลกแยก ทำให้คะแนน Dense ต่ำ แต่ BM25 สามารถจับคู่คำตรงตัวได้แม่นยำสูง
* **วิธีการตรวจสอบ:** รัน `eval_retrieval.py` เปรียบเทียบผลลัพธ์ระหว่าง Dense Only กับ Sparse Only
* **การแก้ไขจริงใน Source Code:**
  * เปิดใช้งาน `USE_HYBRID = True` ใน `config.py`
  * รวมอันดับใน `src/hybrid_retriever.py` ด้วยสูตร Reciprocal Rank Fusion (RRF: $k=60$):
    $$\text{RRF Score}(d) = \frac{1}{60 + \text{Rank}_{\text{dense}}(d)} + \frac{1}{60 + \text{Rank}_{\text{bm25}}(d)}$$

#### 🔴 ปัญหาที่ 3.2: บั๊กการตัดคะแนนตกหล่น (Dual Thresholding Bug) — *ปัญหาที่เกิดขึ้นจริงและแก้ไขแล้ว*
* **ปัญหาที่เกิดขึ้นจริงหน้างาน:** เดิมโค้ดใน `src/hybrid_retriever.py` คัดกรองเฉพาะ `dense_score >= 0.35` ปรากฏว่าคำถามที่มีคำศัพท์เฉพาะทาง เช่น *"กล้องโทรทรรศน์อวกาศเจมส์เวบบ์ (JWST)"* ได้คะแนน BM25 สูงมาก (> 18.0) แต่ Dense ได้เพียง 0.28 ส่งผลให้เอกสารคำตอบจริง **ถูกระบบตัดทิ้งไป** และระบบตอบว่าไม่พบข้อมูล
* **วิธีการตรวจสอบ:** ตรวจสอบคะแนนดิบใน `outputs/retrieval_results.json` พบว่าคำถามเชิงเทคนิคหลายข้อถูก Filtered Out ทั้งที่ BM25 ได้อันดับ 1
* **การแก้ไขจริงใน Source Code (`src/hybrid_retriever.py` บรรทัด 180–187):**
  ```python
  # ปรับเป็น Dual Threshold Logic เพื่อรองรับคำศัพท์เฉพาะทาง
  valid_results = [
      res for res in hybrid_results
      if res.get("dense_score", 0) >= 0.25 or res.get("bm25_score", 0) >= 15.0
  ]
  ```
  *ผลลัพธ์:* คำถามเชิงเทคนิคผ่านการคัดกรอง 100% แก้ปัญหาการตัดข้อมูลทิ้งได้อย่างสมบูรณ์

### 🎯 ขั้นตอนที่ 4: Re-ranking & Context Assembly (การจัดอันดับซ้ำ)

## 4. การวิเคราะห์ผลการทดสอบเชิงวิศวกรรม (Engineering Analysis)

1. **การวิเคราะห์ Recall Ceiling (Hit@10 = 100.00%):** ทุกวิธีการค้นหาสามารถดึงเอกสารเป้าหมายเข้ามาอยู่ในกลุ่ม Candidate Top-10 ได้ครบ 100% ยืนยันว่าขั้นตอน Chunking (`CHUNK_SIZE = 400`, `CHUNK_OVERLAP = 50`) รักษาความสมบูรณ์ของบริบทได้อย่างมีประสิทธิภาพ ไม่มีข้อมูลตกหล่น
2. **การเปรียบเทียบระหว่าง Lexical vs Semantic:** 
   * **Sparse (BM25):** ทำคะแนน Hit@1 และ MRR ได้ 1.0000 เนื่องจากชุดคำถามใน Golden Set มีคำศัพท์ทางเทคนิคตรงตัว (*JWST, หลุมดำ, ซูเปอร์โนวา*) ซึ่งเป็นจุดเด่นของการจับคู่คำตรงตัว
   * **Dense (FAISS):** ได้ Hit@1 ที่ 93.33% เนื่องจากเวกเตอร์ MiniLM มีการเกลี่ยน้ำหนักความหมายของคำศัพท์เฉพาะทาง ทำให้เอกสารเฉลยบางข้อตกไปอยู่อันดับ 2 หรือ 3
3. **เหตุผลที่ระบบจริงต้องใช้ Hybrid Search (RRF):**
   * ในการใช้งานจริง ผู้ใช้มักใช้ภาษาพูดหรือคำพ้องความหมาย (Synonyms เช่น *"ดาวดวงไหนร้อนที่สุด"* แทน *"ดาวเคราะห์ที่มีอุณหภูมิพื้นผิวสูงสุด"*) ซึ่ง BM25 จะค้นหาล้มเหลว
   * การใช้ Hybrid RRF จึงเป็นการสร้างความทนทาน (Robustness) ต่อทั้งคำศัพท์เฉพาะทางและภาษาธรรมชาติ โดยแลกกับ Latency ที่เพิ่มขึ้นเพียง 2.3 ms (20.5 ms) ซึ่งยังคงเป็น Real-time Latency ที่ยอมรับได้ในระดับงานอุตสาหกรรม
